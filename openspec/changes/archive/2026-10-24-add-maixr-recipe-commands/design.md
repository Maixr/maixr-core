# Design

## Context

`MaixrCommands` 已随拉取落地（362 行，单文件命令族），`MaixrMod` 构造器已挂
`RegisterCommandsEvent` 监听。设计要点在于：产物是**脚本文本**而非配方注册，
本模组与 KubeJS 完全解耦；以及为何采用「快捷栏 = 材料、副手 = 产物」的取材约定。

## Goals / Non-Goals

**Goals:**

- 一条命令得到一份「即贴即用」的 KubeJS 脚本，覆盖整合包常用配方类型
- 输出可点击复制，聊天栏不刷屏
- 查询能力（id 清单 / 结构转储）支撑逆向排查既有配方

**Non-Goals:**

- 不加载、不校验、不执行 KubeJS 脚本（KubeJS 非本模组依赖）
- 不做配方数据包生成（.json 输出）——整合包玩法约定走 KubeJS
- 不处理物品组件/NBT 粒度（脚本只写物品 id；需要组件的配方手动改）

## Decisions

**D1 只生成文本，不执行配方**
脚本以聊天消息给出，玩家自行贴入 `kubejs/server_scripts`。理由：与 KubeJS
版本、加载时机完全解耦，本模组零依赖、零执行风险；生成即复制的工作流比
「模组直接注册配方」更符合整合包调参习惯（可改可撤）。

**D2 `event.remove` 前缀 + 显式 `.id()`（生成即覆盖）**
每条脚本（除 `list-remove`）以 `event.remove({output:…});` 开头、以
`.id('maixr:<路径>[_<类型>]')` 结尾。理由：同产物旧配方（原版或上一次生成的）
残留在脚本集里会造成「配方改了但没生效」的排查黑洞；固定 `maixr:` 前缀让
本命令的产物可追溯、可整体清理。替代方案「不带 id 让 KubeJS 自动编号」——
否决：无法精准 remove 与覆盖。

**D3 取材约定固定「快捷栏 = 材料、副手 = 产物」**
单命令无 GUI、无参数选择器，箱子/背包里摆好按一下即得。烹饪类收窄到 0 号位、
锻造固定 0/1/2 三格，避免「材料顺序歧义」。下划线别名保留旧使用习惯。

**D4 模组配方走类型白名单（switch 硬编码模板）**
Create/Mekanism/AE2 只开放手动核实过的高频类型；未支持类型明确报错并列出
可用清单。替代方案「按 RecipeSerializer 反射通用生成」——否决：模组配方
参数结构差异大（流体/气体/概率/处理时间），通用生成极易产出不可用脚本，
白名单保证每条模板都真实可跑。

**D5 模板内固定参数宁可保守**
`injecting`/`purifying` 气体固定 `mekanism:oxygen`、`metallurgic` 注入剂固定
`mekanism:redstone` 用量 10、AE2 `inscriber` 三输入同物并附「请按实际修改」
注释。理由：这些参数无法从背包取材推断，给合理默认 + 显式注释比静默猜错好。

**D6 权限等级 0 + 仅玩家执行**
命令只读 RecipeManager 与玩家自己的背包，无破坏性；整合包单人/局域网场景
不设门槛。非玩家来源在取材类子命令上以「需要玩家」明确失败。

## Risks / Trade-offs

- [KubeJS 语法随版本漂移，生成的脚本在旧/新 KubeJS 下不解析] → 模板按整合包
  当前 KubeJS（1.21.1 线）事件 API 写死；验证任务含「贴入整合包实测」，
  mod 侧不做版本探测。
- [`COPY_TO_CLIPBOARD` 内容过长被客户端限制] → 单脚本体量 < 1 KB，远低于
  聊天组件限制；`recipe-ids` 用逐条短消息规避单消息超长。
- [产物含组件（如附魔书）时脚本丢失组件] → 已知取舍：脚本只写物品 id，
  spec 明确不处理组件粒度；需要时玩家手动补 `{...}` 组件段。

## Migration Plan

纯新增命令族，无数据迁移；回滚 = 移除注册监听（git revert）。
`openspec/config.yaml` 上下文的「已移除系统」清单修正随本变更归档执行。
