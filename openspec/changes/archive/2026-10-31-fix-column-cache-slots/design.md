# Design

## Context

见 proposal.md「Why」：列缓存的槽位索引写死 `>>> 58`，使 4096 槽实际只有 64 槽可达。

约束（shape the approach）：

- 缓存是**直接映射表**：`slot → (key, value)`，命中要求 `keys[slot] == key`，
  未命中回落 `computeUncached` 并在同一 `slot` 覆写。**槽位选择不影响返回值**，
  因为任何键都不会读到别人的值——它只会多算或复用一次相同的求值结果。
- 缓存是 **per-instance ThreadLocal**（必须 per-instance：下界/末地/离线掩码同列
  输出不同；必须 ThreadLocal：worker 并发下保证「位置↔值」原子配对）。
- `computeUncached` 是纯 2D 函数（撕裂深度只由 (x, z) 决定，与 y 无关）。
- 本机为 4 核 8 线程（i7-4790），`view/simulation distance = 10`，基准协议固定
  9 个远区域取中位数。

## Goals / Non-Goals

**Goals:**

- 让 `CACHE_SLOTS` 声明的容量真正生效，且对任意 2 的幂容量都成立。
- 保持**值恒等**：返回值、生成输出、同种子确定性均不改变。
- 把修复后的实测读数与作废的旧归因写进文档，恢复文档与代码一致。

**Non-Goals:**

- 不重新评估 `CACHE_SLOTS` 的最优取值（4096 维持；修复后已达标，调参无收益动机）。
- 不做新的 JFR 归因（比值已 ≤1.5×，归因不再阻塞任何决策）。
- 不清理 `_docs/生成性能测量.md` 的历史读数（保留原始数字，只标注失效原因）。

## Decisions

**D1 用 `SLOT_SHIFT` 派生位移，而非写死常量。**

`SLOT_SHIFT = 64 - Integer.numberOfTrailingZeros(CACHE_SLOTS)`，索引取
`(int) (key * GOLDEN >>> SLOT_SHIFT) & (CACHE_SLOTS - 1)`。
位移量由容量派生，改 `CACHE_SLOTS` 时不会再出现「容量与位移脱节」这一类 bug；
末位再与掩码相与，使非 2 的幂容量也不越界（虽则本用例恒为 2 的幂）。

> 备选：写死 `>>> 52`（4096 的对应值）。更少代码，但把同一个坑留给下一次调容量——
> 正是这次踩坑的成因，弃用。

> 备选：改双路组相联 / 开放寻址以进一步降碰撞。修复后比值 0.76× 已达标，
> 复杂度不值（沿用 2026-10-25 `fracture-perf-leaps` design D1 的结论）。

**D2 不改 `CACHE_SLOTS` 取值（维持 4096）。**

修复后实测 0.76×，已低于 1.5× 参考线；容量翻倍只会增加内存（每实例每线程
+64KB）而无明确收益。保留 4096 亦与既有 design 记录一致。

**D3 验收口径沿用「值恒等优化」两级验收。**

按主 spec「生成输出跨版本效果稳定」：值恒等优化要求逐块相同率不低于基线自漂移
水平。本次取两个对照：

1. **同构建重跑**（修复版 vs 修复版，两个全新世界）——自漂移上界；
2. **修复版 vs `_bench-data/baseline-regions/broken`**——注意后者是 **L2 短路之前**
   采集的「优化前区块集」，因此该对比同时含 L2 的行为级差异，不能用「值恒等」
   标准去要求它；按行为级验收线（≥85%）判定，并要求差异性质为材质微差。

**D4 基准分母重采，不用历史 6.58s。**

`_docs` 里的原版基线 6.58s 采于 2026-10-25；跨日跨会话的机器状态（后台负载、
JIT、磁盘缓存）不可控，直接作分母会引入未知偏差。本次在**同机同日同会话**
重采原版基线（7.11s）作分母，并把旧读数保留为历史参考。

**D5 旧归因标注失效而非删除。**

`_docs/生成性能测量.md` 的 L1 复测表与 JFR 归因表，其数字是真实采集的，只是
**解释**错了（把「容量从未生效」误读成「容量无收益」）。保留原始读数并插入
勘误段落，比删除更利于追溯——符合项目「文档要记录为什么这样做与踩过的坑」的
规范。

## Risks / Trade-offs

- [修复后墙钟变快，验收对比会不会把「快」误当「对」] → 验收只看输出哈希
  （sections / BE），与耗时无关；耗时仅用于性能口径，两者分开报告。
- [97.14% < 同构建自漂移 97.70%，是否说明修复改变了输出] → 不：修复不改变
  返回值（D1 论证）。差异来自 ① 对照集含 L2 短路前状态，② 伴生岛模板使用世界
  随机的既有漂移。要求差异区块集中于伴生岛模板随机文件——与既往归档的漂移
  模式一致即可；出现 air↔实体翻转或结构性形态变化才判失败。
- [缓存生效后内存占用上升] → 容量本身未变（4096 × 16B = 64KB/线程/实例，
  与修复前声明的相同）；修复只是让这部分内存第一次真正被用到。
- [文档勘误牵动已归档变更的结论] → 已归档变更的 artifacts 是历史记录，
  不回改；只在 `_docs` 与主 spec 里更正现行结论，并在 spec delta 里写明更正
  事实与日期。

## Migration Plan

1. 改 `FractureDensityFunction`（D1），`./gradlew build`。
2. 基准：同机同日重采原版基线 → 破碎世界两次（两个全新世界）→ 取中位数。
3. 值恒等验收：`_tools/mca_diff.py` 逐块对比（两个对照，见 D3）。
4. 文档更正：`_docs/破碎世界.md`、`_docs/生成性能测量.md`、主 spec。
5. 版本号 2.0.0 → 2.3.1，构建发布 jar，打 tag v2.3.1 并发布。

回滚：单项 `git revert` 即可（一处索引改动）；无存档兼容性问题（缓存不落盘）。
