# 生成性能测量（随机传送基准 + 火焰图抓取）

破碎世界随机传送后「TPS≈0 持续几十秒 + 区块缓慢补齐」的定位手册。
工具面：`/maixr bench`（本模组自带，OP 权限）+ spark（外部模组，按需放入 mods）。
原理与实现见 `MaixrBench` 类注释；变更记录：`openspec/changes/2026-10-25-gen-perf-bench`。

## 一、环境控制（不满足则数据不可信）

| 控制项 | 要求 | 原因 |
| --- | --- | --- |
| 种子 | 固定并记录（`level.dat` 或创建时输入） | 基准目的地序列由「世界种子 + 参数 + 序号」确定性派生，同种子同参数坐标序列逐项相同 |
| 世界目录 | **每轮全新**（或删除 `region/`） | region 文件缓存会让第二轮同坐标明显变快（口径陷阱见第六节） |
| 热身 | 每次测量前先随机传送一次，丢弃数据 | JIT 冷启动会污染第一组数字 |
| 环境 | release jar + dedicated server 优先 | runClient 集成服务端混入客户端帧时间 |
| 记录项 | `view-distance` / `simulation-distance` / CPU 核数 | 积压规模 = (2×view+1)²；worker 数影响吞吐，对比时必须同参 |

命令口径（与代码常量一致）：

```text
/maixr bench tp <次数> [最近距离] [最远距离]   # 缺省 3000~20000；次数上限 1000
/maixr bench stop                              # 中断并输出已完成部分
```

- 基线：会话开始先静默采 10 tick 取中位数；恢复判定：末次传送后连续 20 tick
  MSPT ≤ 基线 × 1.2（或 200 tick 超时）。
- 输出：聊天栏 + 服务器日志双通道（日志便于 dedicated server 事后取证）。

## 二、spark 火焰图抓取（归因的一步）

1. 把 spark jar 放入服务端 `mods/`（客户端不必装），重启。
2. 玩家进入世界 → 执行一次热身传送（丢弃）。
3. 执行 `/maixr bench tp 5 3000 20000`，**立刻**跟一句：

```text
spark profiler --timeout 60
```

4. 60 秒后 spark 自动停止并给出查看链接。看 **Server thread** 的栈顶分布：
   - `ServerChunkCache.pollTask` / 区块生成任务内部（主线程内联帮跑区块任务）→
     继续看里面的子栈，按第五节决策表定位；
   - `FragmentRoadNetwork` / `VoidDebrisCleanup` / `GeodeBlobCleanup` 直接出现在
     主线程栈顶 → 加载期挂钩实锤（检查 `config/maixr-common.toml` 的
     `bridgesEnabled` / `geodeCleanupEnabled` 是否为 true）；
   - 区块晋升 / 实体加载 / 发包占比高 → 天空结构带来的方块实体密度问题。
5. 无 spark 的兜底：vanilla 自带 `/perf start` / `/perf stop`（输出可读性差，仅应急）。

| worker 样本 inclusive | 256 槽 | 4096 槽 |
| --- | --- | --- |

  > 「256 槽 vs 4096 槽」实为同一配置——本条的对照不成立。修复后墙钟从 2.38×

  （碰撞对 8→2，不再有可测风暴），维持 4096。
  > **2026-10-31 更正**：修复后 `CACHE_SLOTS=4096` 真正生效，维持该值成立；
  > 但当时的「~24% 无法再消」判断来自未生效配置，已不适用。
- 处置（design D5）：L1 无语义风险总是保留（为将来更宽列批次/多实例兜底）；

## 五、栈顶决策表

| Server thread 火焰图栈顶 | 病灶 | 对应修复方向 |
| --- | --- | --- |
| `Unsafe.park` 占主导，祖先链是 `Entity.setPosRaw` → `Level.getChunk` → `ServerChunkCache.managedBlock` | **传送同步等待**：原版实体跨区块移动会同步取目标区块 FULL，生成多慢主线程就冻结多久（2026-10-25 实测主病灶，23.8s/次） | 缩短单区块生成成本（worker 侧优化）等比缩短冻结；模组自身无主线程帧则 M2/M3 排除 |
| `pollTask` 内是 noise/density 栈（`FractureDensityFunction` / `PlateFieldLogic`） | 嫌疑①：列缓存修复后噪声阶段仍贵 | 深挖 fracture 每区块调用次数、震中激活缓存 |
| `pollTask` 内是 features/结构栈（`MaixrDressingPass` / `SkyStructurePlacer` / 模板放置） | 嫌疑②：装饰阶段是大头 | 结构池缓存、`MAX_ATTEMPTS` 收紧、dressing 微优化 |
| `FragmentRoadNetwork` / 加载期清理直接在主线程栈 | M2：加载期挂钩 | 挂钩异步化或更紧 tick 限额（改动最小收益最大） |
| 晋升 / 实体 / 方块实体 / 发包占比高 | M3：FULL 晋升被放大 | 排查天空结构里的容器密度 |
| 以上都不明显，worker 线程图里才见热点 | 纯吞吐问题 | 按 ms/区块成本逐项优化（嫌疑①②） |

worker 侧归因用 JFR 最可靠（spark 内置 java 引擎在 dev 实测只采样到 Server thread）：
`jcmd <pid> JFR.start name=gen settings=profile filename=gen.jfr duration=70s` →
`jfr print --events jdk.ExecutionSample gen.jfr` → `_tools/jfr_tops.py` 聚合。

背景机制：区块生成阶段跑在 worker 线程池，主线程只在等待玩家区块 FULL 时经
`ServerChunkCache` 的 mailbox/内联帮跑路径参与生成——所以「单区块生成成本高」
最终会以主线程 TPS≈0 的形式表现出来，掉 TPS 总时长 ≈ 积压区块数 × 单区块成本。

## 六、口径陷阱（读数前必看）

1. **region 缓存**：第二轮跑同种子同参数，坐标序列相同但明显更快——必须全新世界目录。
   基准只承诺「坐标序列确定性」，不承诺「耗时确定性」。
2. **墙钟含网络往返**：同维度传送的目的地区块 ticket 要等客户端确认传送后才迁移，
   dedicated server 上测得值略偏高（测得值 ≥ 纯生成成本）。
3. **探测/轮询开销不扣除**：`getBaseHeight` 单列离线求值（毫秒级）+ 每 tick 一次
   `getChunkNow` 判空，误差方向同上。
4. **连续传送互相污染**：上一目的地的积压未排空即开始下一次传送，单次墙钟偏大——
   这是有意设计（对齐玩家「连续随机传送」的真实负载），跨组对比时保持次数一致即可。
5. **报告与聊天栏**：聊天栏可能被客户端消息上限截断，以日志为准做存档。
6. **MSPT 峰值不含阻塞时段**：主线程被同步取块阻塞期间没有 tick 在跑，vanilla 环形
   缓冲里只有阻塞前后的正常 tick——「墙钟 21s / MSPT 峰值 21ms」并存即此现象，
   判断冻结严重度以**墙钟**为准。
7. **RCON 会话超时 ≠ 失败**：对阻塞中的服务器发 RCON 命令，应答要等主线程解锁才返回，
   超时只说明「阻塞正在发生」。
