# 「破碎」世界类型

> **注**：本文中与「伊甸修复」相关的章节（取样源 pristine / 重生世界 reborn /
> 修复引擎等）所述系统**已从本模组整体移除**，内容仅作历史参考。


> **一句话**：选了「破碎」，**主世界本身就是破碎世界** ——
> 真实地形 + 渐变虚空，出生点附近几乎完好、越往外越碎，
> 原点 (0,160,0) 有一座开局空岛，玩家出生/无床复活都落在岛上的草方块上。
>
> **★ 地形与结构完全解耦**：地形纯按公式挖（远处就是 95% 虚空），
> 而结构（村庄/要塞/末地传送门）在虚空里**照常完整落地** —— 悬空的残存遗迹。
> 详见「结构处理」一节。

## 三种世界类型各自的形态

| 世界类型 | 主世界生成器 | 地形 | 出生 |
|---|---|---|---|
| **默认** | `minecraft:noise`（原版） | 原版地形 + biome | 原版地表 |
| **空岛** | SkyblockBuilder 的空岛生成器 | 空岛平台 | 主世界空岛（SkyblockBuilder 自己管） |
| **破碎** | `maixr:broken_overworld` | 真实地形 + 渐变虚空 | 主世界 (0,160,0) 的开局空岛 |

## 一、渐变虚空（`BrokenOverworldChunkGenerator`）

虚空**不是均匀的** —— 出生点附近基本完好，越往外越碎。

判据是区块到原点的切比雪夫距离 `d = max(|chunkX|, |chunkZ|)`：

| d（区块） | 距离（格） | 虚空比例 |
|---|---|---|
| 0（出生点） | 0 | **20%** |
| 25 | ≈400 | 57.5% |
| **50** | **≈800** | **95%** |
| >50 | — | 恒定 95% |

中间**线性过渡**（`voidChance(x,z)`）。三个常量在类顶部，想调手感直接改：

```java
public static final double NEAR_VOID_CHANCE = 0.20D;   // 出生点
public static final double FAR_VOID_CHANCE  = 0.95D;   // 最远
public static final int    RAMP_CHUNKS      = 50;      // 多少区块后到最碎（≈800 格）
```

> 过渡带收窄到 800 格 —— 出岛走一小段就能明显看出"越来越碎"，比原来 4000 格直观得多。

判定用**确定性哈希**（`roll01`，不依赖世界种子）—— 同一个坐标永远得到同一个结果，
所以不会出现"走过去又变回来"。

### ★★★ 结构处理：地形与结构【完全解耦】

**这里走了 5 版弯路，教训值得记下来。**

| 版本 | 做法 | 结果 |
|---|---|---|
| v2 | 无脑挖虚空 + 虚空区块跳过 `applyBiomeDecoration` | ❌ **村庄真被截断** |
| v3 | 保护 `hasAnyStructureReferences()` 的区块 | ❌ 虚空率从 92.7% 掉到 **50.8%** |
| v4 | 保护"精确 piece bbox 相交"的区块 | ❌ 仍有 44.8% 被保护 |
| **v5（现在）** | **地形纯按公式挖；结构一律照常落地** | ✅ 虚空率 = 92.7%，结构完整 |

#### v2 村庄被截断的真凶

`ChunkGenerator.applyBiomeDecoration` 内部干两件事：

```java
1. 放地形装饰（树、草、矿…）
2. for (Structure structure : ...)
       startsForStructure(sectionpos, structure)
           .forEach(start -> start.placeInChunk(...));   // ← 结构真正写方块！
```

v2 在这个方法里对虚空区块 `return` 了 —— 结果**连结构一起跳过**，
落在虚空区的半座村庄**从来没被放置过**。

> **结论：结构能不能落地，跟"那里有没有地形"毫无关系。**
> `StructurePiece.postProcess()` 是**无条件 `setBlock`** 的，不依赖脚下地形。

#### v3/v4 为什么也错

试图"保护有结构的区块"必然要留地形，而**大型结构的覆盖范围本身就极广**（实测存档数据）：

| 结构 | 覆盖区块数 | Y 范围 | 类型 |
|---|---|---|---|
| `minecraft:mineshaft` | **14433** | -61..52 | 地下 |
| `repurposed_structures:mineshaft_ocean` | 9175 | -23..31 | 地下 |
| `minecraft:trial_chambers` | 3922 | -53..23 | 地下 |
| `data_energistics:meteorite` | 1183 | 19..62 | 地表 |
| `minecraft:village_desert` | 450 | 60..90 | 地表 |
| `ae2:meteorite` | 810 | 34..110 | 地表 |

光是废矿就横扫 1.4 万个区块 —— 保护它等于毁掉整个"破碎"效果。

#### ✅ v5 的正确做法

```java
// ① 地形：只看坐标，不掺任何结构信息
private boolean isVoidedChunk(ChunkAccess chunk) {
    return isVoided(chunk.getPos().x, chunk.getPos().z);
}

// ② 结构：这两个阶段【绝不跳过】（虚空区块也照常跑）
@Override public void createStructures(...)     { super.createStructures(...); }
@Override public void applyBiomeDecoration(...) { super.applyBiomeDecoration(...); }

// ③ 只有纯地形阶段跳过
fillFromNoise / buildSurface / applyCarvers  ->  虚空区块 return
```

结果：**地形是碎的，结构是完整的**。村庄有完整地基与房屋、
要塞与末地传送门一定拿得到，它们只是**悬在虚空里** ——
正是破碎世界该有的"残存遗迹"氛围。

| 生成阶段 | 虚空区块 |
|---|---|
| `fillFromNoise` | **跳过**（无地形） |
| `buildSurface` | **跳过** |
| `applyCarvers` | **跳过** |
| `createStructures` | ✅ 照常 |
| `applyBiomeDecoration` | ✅ **照常（结构在这里落地）** |

> ⚠️ 只对**还没生成过**的区块生效；老存档已落盘的区块保持原样。

> 💡 副作用可忽略：虚空区块里没什么地表可点缀，绝大多数 `Feature` 会自己
> 找不到落点而放弃；换来的是结构不消失，非常划算。

## 一点五、破碎结构（天空随机生成任何结构）

> **一句话**：「破碎」世界里，**天空（y ≥ 201）里会随机悬浮着各种结构** ——
> 村庄、前哨站、要塞、远古城市、试炼密室、末地城、热气球、星舰、模组里的飞船/神殿……
> **全部结构都能上天**，平均**每 100 个区块一座**。

### 规则

| 项 | 值 |
|---|---|
| 生效范围 | **只**在「破碎」世界类型的主世界 |
| 概率 | **1 / 100**（每区块 1%；平均每 100 区块一座） |
| 高度 | 结构**底部** y ≥ **201**，在 [201, 319-结构高度] 内随机 |
| 池子 | 服务器上**所有已注册结构**（原版 + 全部模组，自动收集，不硬编码） |

### ★★ 浮空薄板 bug 与两版修法

**症状**：世界高空随机出现**大片浮空的、只有两三格高的区块**，中间还有洞。

**根因**：Beardifier（原版的"胡须器" = **地形适配**机制）。

```java
// NoiseBasedChunkGenerator.createNoiseChunk 内部：
NoiseChunk.forChunk(chunk, randomState,
        Beardifier.forStructuresInChunk(structureManager, chunk.getPos()), ...)

// Beardifier.forStructuresInChunk 内部：
startsForStructure(chunkPos, s -> s.terrainAdaptation() != NONE)
    .forEach(start -> {
        for (StructurePiece piece : start.getPieces()) {
            if (piece.isCloseToChunk(chunkPos, 12))          // 12 格内
                add(new Rigid(piece.getBoundingBox(), terrainAdjustment, ...));
        }
    });
```

只要结构带 terrain_adaptation（村庄/前哨站都是 beard_thin），
原版就会在它周围 **12 格内按它"长地形"**。我们把结构抬到 y≥201 的虚空里 ——
Beardifier 算不出合理高度，**就地摊成两三格厚的浮空薄板**。

#### ❌ 第一版修法（已废弃）：把带地基的结构全部剔除

按 terrain_adaptation == NONE 过滤，264 个结构里只放行 175 个。
**问题：村庄、前哨站、要塞、远古城市、试炼密室全都上不了天** ——
玩家明确要求「我就要让它们上天」。

#### ✅ 第二版修法（现行）：在 BIOMES 阶段临时摘掉天空结构的 references

BrokenOverworldChunkGenerator.createBiomes：

```java
Map<Structure, LongSet> original = SkyStructurePlacer.maskSkyReferences(chunk, structureManager);
if (original == null) {
    return super.createBiomes(randomState, blender, structureManager, chunk);
}
// super.createBiomes 是异步的 → 还原必须挂 whenComplete（不能用 try/finally）
return super.createBiomes(randomState, blender, structureManager, chunk)
        .whenComplete((result, error) -> chunk.setAllReferences(original));
```

Beardifier 看不到这些结构 → **不长任何地形**；
FEATURES 阶段 references 已还原，applyBiomeDecoration 照常把结构方块放出来。

**★ 时机必须是 BIOMES，不能是 NOISE**

| 事实 | 后果 |
|---|---|
| ChunkAccess.noiseChunk **永久缓存**（if (this.noiseChunk == null)，全 jar 无人重置） | 读一次就定型 |
| 它在 **BIOMES 阶段**（ChunkGenerator.doCreateBiomes）就创建 | **比 NOISE 还早** |
| 等到 fillFromNoise 再屏蔽 | Beardifier 早读完了，**完全无效** |

**★ 为什么摘 references 是安全的（无竞态）**

| 问题 | 答案 |
|---|---|
| Beardifier 读谁的 references？ | **本区块自己的**（level.getChunk(chunkPos, STRUCTURE_REFERENCES)） |
| 邻居的 createReferences 读什么？ | 读我们的 **starts**，不读 references → 不受影响 |
| 还有谁需要本区块 references？ | 本区块的 applyBiomeDecoration（FEATURES），那时已还原 |
| 异步安全吗？ | super.createBiomes 是 supplyAsync，还原挂 whenComplete |

**★ 判据**：按 pieces 现算底面 >= MIN_Y - 4 才算天空结构
（**不能**用 StructureStart.getBoundingBox() —— 它带缓存，被 move 过之后就过期）。
同一结构类型可能既有地面实例又有天空实例，只有"这份引用解析出的 start 清一色是天空结构"时才摘。

### 实现要点

**① 走原生的 StructureStart 注册路线**（而不是自己一次性放完）

在 `createStructures` 阶段调 `structure.generate(...)` 拿到 `StructureStart`，
`move` 上天后调 `StructureManager.setStartForStructure(...)` 登记进区块。
之后**原版的引用机制自动接管**：

```
STRUCTURE_STARTS      我登记 start
STRUCTURE_REFERENCES  createReferences 扫本区块±8，把 bbox 相交的区块登记为引用
FEATURES              applyBiomeDecoration -> startsForStructure -> placeInChunk
                      每个区块只放自己那一片
```

这样**跨区块、局部放置、性能全部由原版保证** —— 不会因 `WorldGenRegion` 写半径限制而被截断。

**② ★ dry-run 安全校验（关键）**

`StructurePiece.move()` 的语义是**只移动碰撞箱**，真正方块坐标由子类自己维护：

| 类 | 同步真实坐标？ |
|---|---|
| `TemplateStructurePiece` | ✅ 更新 `templatePosition` |
| `PoolElementStructurePiece` | ✅ 更新 `position` |
| `MineshaftPieces` | ❌ 覆写了但**没同步走廊起点** |
| 未知模组 piece | ❓ 可能根本没覆写 |

所以搬移**之前**先逐个 piece 试 `move`，检查包围盒是否真的跟着动；
**任何一个不听话 → 整座结构放弃**。宁可不生成，也不要在地面留一堆搬不动的残骸。

**③ 不用 `StructureStart.getBoundingBox()` 算高度**

它会把结果**缓存**在 `cachedBoundingBox` —— 搬移后缓存就过期了。
代码里改用 `piecesBBox(pieces)` 现算。

### 为什么不需要判世界类型

`maixr:broken_overworld` 这个生成器**只被** `world_preset/broken.json` 的主世界引用，
所以"`tryPlace` 被调用"**本身就等价于**"当前是破碎世界类型的主世界"：

| 世界类型 | 主世界生成器 | 会走到这吗 |
|---|---|---|
| 默认 | `minecraft:noise` | ❌ |
| 空岛 | SkyblockBuilder 的生成器 | ❌ |
| **破碎** | **`maixr:broken_overworld`** | **✅** |
| 下界 / 末地 / 其它维度 | 各自的生成器 | ❌ |

### 调参

```java
public static final int CHANCE_DENOMINATOR = 100;   // 越大越稀
public static final int MIN_Y = 201;                // 最低高度
public static final int TOP_MARGIN = 2;             // 顶部余量
```

### 排查

日志里最多报 40 条成功 / 20 条放弃（★ 调试日志已注释，见「八」开头的说明）：

```

```

## 一点七、空域浮岩（陨石团簇 + 粗矿块）

> **一句话**：天上（y=110~170）飘着的<b>不只是灰色陨石</b> ——
> **35% 陨石团簇 + 65% 各种粗矿块**。

### 为什么改

玩家反馈「天上漂浮的陨石块太多了」。原来这个 Feature **100% 只放灰色陨石**，
整片天空都是同一种暗灰色，很单调。

### 改成什么

| 种类 | 比例 | 外形 | 方块 |
|---|---|---|---|
| **陨石团簇** | 35% | 椭球 2~4 × 1~3 × 2~4 | 外壳 `ae2:sky_stone_block`（可粉碎成陨石粉）、内核 `ae2:smooth_sky_stone_block` |
| **粗矿块** | 65% | **圆球** r=2~3 | 从 16 种粗矿块里随机一种，通体填充 |

### 粗矿块池（16 种，按装的模组自动过滤）

| 模组 | 方块 |
|---|---|
| 原版 | `raw_iron_block` / `raw_copper_block` / `raw_gold_block` |
| 机械动力 | `create:raw_zinc_block` |
| 通用机械 | `block_raw_osmium` / `block_raw_lead` / `block_raw_tin` / `block_raw_uranium` |
| 通用机械扩展 | `mekanism_extras:block_raw_naquadah`、`mekmm:block_raw_silver` |
| 其它 | `neoecoae:raw_tungsten_block` / `raw_aluminum_block`、
`pasterdream:raw_titanium_block`、`anvilcraft:raw_titanium_block` / `raw_tungsten_block`、
`enderio_evolution:crude_steel_block` |

> **★ 已剔除 `justdirethings:raw_ferricore_ore`**（JDT 的核源铁）：
> 它不是"地下能挖到的粗矿块"，而是 JDT 自己那套资源体系里的特殊方块
> （`blockstates/raw_ferricore_ore.json`，带专属指南书/工具/盔甲）。
> 按需求"只要地下有的矿的粗矿块"移除。

**★ 没装的模组的方块会自动剔除** —— `orePool()` 首次调用时按注册表过滤一次，
所以不会在世界里放空气。启动日志会打（★ 该行已注释，见「八」开头的说明）：

```
[空域浮岩] 粗矿块池：16/16 种可用（其余模组未装）
```

### 形状（圆润度）

方块世界里"球"必须体素化，严格按数学椭球（`d <= 1.0`）出来会有明显棱角。
所以把判定阈值**放宽**，把边缘补齐：

| 种类 | 阈值 | 半径 | 说明 |
|---|---|---|---|
| 陨石团簇 | `1.22` | 2~4，三轴接近等长 | 实测 147 块（理想球 113）——圆润但有碎石感 |
| 粗矿块 | `1.25` | 2~3，**三轴等长** | 实测 57 块（理想球 34）——饱满的小球 |

> **★ 阈值是离散跳变的**（实测）：r=3 时 1.22 → 147 块，1.25 → 171 块，1.35 → 179 块（退化成方块团）。
> 所以别凭感觉调，改之前先用体素模拟看一眼形状。

> **旧版的问题**（玩家反馈"形状太难看"）：
> - 陨石 `ry` 只有 1~3 而 `rx/rz` 是 2~4 → 出来是**压扁的饼**
> - 矿块做了"边缘随机剔除"想模拟锯齿感 → 实际是**带缺口的方块团**
> - 现在三轴接近等长 + 阈值补齐 = 圆润的球

### 密度

`placed_feature/sky_stone_cluster.json`：

```json
{ "type": "minecraft:rarity_filter", "chance": 8 }
```

`rarity_filter` 的真实语义是 `nextFloat() < 1/chance`（`RarityFilter` 源码实测），
所以 **chance=8 = 每个区块 1/8 概率**。比原来的 12 密 50% ——
因为现在 65% 是更小的粗矿块，需要更密才不显空。

### 调参

| 想改什么 | 改哪 |
|---|---|
| 陨石/矿块比例 | `SkyStoneClusterFeature.METEOR_SHARE = 0.35D` |
| 整体密度 | `placed_feature/sky_stone_cluster.json` 的 `chance` |
| 高度范围 | 同上，`height_range` 的 `min_inclusive` / `max_inclusive` |
| 加矿种 | `SkyStoneClusterFeature.RAW_ORE_IDS` 加一行 |
| 形状圆润度 | `placeBlob` 的 `1.22D`（陨石）/ `placeOreBlob` 的 `1.25D`（矿块） |

### 生效范围（没变）

| 世界类型 / 维度 | 长浮岩？ |
|---|---|
| **破碎**（主世界用 `maixr:broken_overworld`） | ✅ |
| **空岛**（主世界用 SkyblockBuilder 生成器） | ✅ |
| 维度 `maixr:overworld_broken` | ✅ |
| 默认世界类型主世界 | ❌（会有悬空石堆） |
| 其余维度（下界 / 末地等） | ❌ |

## 二、开局空岛（`BrokenIslandHandler`）

### 放什么、放哪

| 项 | 值 |
|---|---|
| 结构 id | `maixr:broken_skyblock` |
| 文件 | `data/maixr/structure/broken_skyblock.nbt`（12×14×12，2016 方块） |
| 放置原点 | **(0, 160, 0)** —— 对齐结构的 (0,0,0) |
| 只放一次 | 靠 `BrokenIslandData`（维度级 `SavedData`，键 `IslandPlaced`） |

放置时机是 `ServerStartedEvent`（服务器完全启动后），并**先强制加载周边区块**
—— `setBlock` 落在未加载区块上会被静默丢弃。

### ★★ 出生点：直接改世界出生点，不传送玩家

**这是踩过两次坑之后定下的做法。**

#### 坑一：传送法（已废弃）

旧版 `MaixrBrokenSpawnHandler` 的做法是「首次进服把玩家 `teleportTo` 进独立维度」。
问题是 `ServerPlayer.findRespawnPositionAndUseSpawnBlock` 在**没有床/重生锚**时的兜底是：

```java
return new DimensionTransition(this.server.overworld(), this, p_352261_);
//                    ^^^^^^^^^^^^^^^^^^^^^^^ 主世界
```

也就是**死后复活会被扔回主世界的世界出生点**。→ 用户实测报告："我死后复活在了主世界。"

#### 坑二：spawnRadius（也踩了）

改成 `setDefaultSpawnPos(岛上草方块, 0F)` 之后仍有问题：
`ServerPlayer.adjustSpawnLocation` 会以出生点为中心、在 **±spawnRadius** 的方形范围内
**随机乱找**一个能站立的位置（`PlayerRespawnLogic.getOverworldRespawnPos` 返回该列的真实地面高度）。

`spawnRadius` 默认 **10** → 搜 21×21 格 → 岛只有 12×12 →
**绝大多数候选点在岛下方的地形上（y≈70）** → 玩家被扔到岛下面。

#### ✅ 现在的做法

```java
overworld.getGameRules().getRule(GameRules.RULE_SPAWN_RADIUS).set(0, server);  // ★ 关键
overworld.setDefaultSpawnPos(岛上的草方块, 0.0F);
```

`spawnRadius = 0` → 搜索范围只剩出生点自身那一列 → `getOverworldRespawnPos` 正好落在岛中心列上。

这样两条路径都落在岛上：
- **首次进服**：`PlayerList.placeNewPlayer` → `getSharedSpawnPos()`
- **无床死亡复活**：`DimensionTransition.missingRespawnBlock(server.overworld(), ...)` → 同上

### 选哪块草方块

`findGrassTop()` 在放置点周围 -4..20 扫描：
1. **只认 `minecraft:grass_block`** —— 岛上还有 podzol / mycelium / moss_block，
   它们也在 `#minecraft:dirt` 标签里，但玩家要的是草方块
2. 要求上方两格是空气（站得下）
3. 挑**离岛中心最近**的那块 —— 避免挑到最边沿、被落点修正一脚踢下岛

找不到草方块时退回「最高可站立方块上方」，再退回归放置点上方（保证不卡流程）。

### 换岛（用户已做过一次，流程保留）

1. 游戏内用 **Structure Saver** 道具导出自定义岛 → `.nbt`
2. 覆盖 `src/main/resources/data/maixr/structure/broken_skyblock.nbt`
3. 如果新岛尺寸/原点变了，同步改 `BrokenIslandHandler.ISLAND_ORIGIN`

### ★ 复活兜底（PlayerRespawnEvent 拉回）

光设出生点还不够：原版 `ServerPlayer.adjustSpawnLocation` 在出生点那一列
"向上找空位、再**向下掉**到有碰撞的地面"。岛只有 12×12 且悬空，
只要出生点列因任何原因（岛边缘、草方块被挖、别的模组改地形）没有碰撞体，
玩家就会一路掉到岛下方 90 格的真实地面上。

所以 `BrokenIslandHandler.onPlayerRespawn` 在玩家**复活完成后**检查落点：
不在岛上、且玩家**没有自己的床/重生锚**（`getRespawnPosition() == null`）时，
强行传送回岛上（`findGrassTop` 重新定位）。日志
（★ 该行已注释，见「八」开头的说明）：
`[破碎空岛] 玩家 xxx 复活点不在岛上，已拉回 ...`。
只在破碎世界类型 + 主世界生效。

> 另外 tag 文件只认 `values`/`replace`/`remove`，**加 `_comment` 会导致解析失败**。

「破碎」世界类型本体在 `data/maixr/worldgen/world_preset/broken.json`，
主世界指向 `maixr:broken_overworld`，下界/末地与普通世界一致。

## 四、怎么检测"玩家选的是破碎世界类型"

世界类型的选择**不会直接写进 level.dat**，但**主世界用的是哪个 chunk generator 一定会被存下来**。

所以 `BrokenWorld.isBrokenWorldType(server)` 就是：

```java
return server.getLevel(Level.OVERWORLD)
        .getChunkSource().getGenerator()
        instanceof BrokenOverworldChunkGenerator;
```

这个判定既是"类型标记"也是"事实"（那个生成器真的会生成破碎地形）。

## 五、独立维度 `maixr:overworld_broken` 的现状

它是**老式**的空岛 + 95% 虚空维度（用 `BrokenSkyblockChunkGenerator`，继承 SkyblockBuilder）：

- **不再是出生地**，玩家不会自动进去 —— 出生点在主世界 (0,160,0) 的开局空岛上
- **保留**，因为老存档里已经生成过区块；结构（村庄/要塞等）在这个维度照常生成，
  只是悬在虚空里

维度本体在 `data/maixr/dimension/overworld_broken.json`（生成器 `maixr:broken_skyblock`，
`layers` 数组铺基岩/泥土/草方块平台）。

> ⚠️ 历史注记：该维度曾是「伊甸修复」体系的修复目标（取样源
> `maixr:overworld_pristine` / 重生世界 `maixr:overworld_reborn` 也隶属该体系）。
> 伊甸工程已整体移除，pristine / reborn 两个维度**已不存在**，没有任何 json 引用它们。

## 六、SkyblockBuilder 全局配置（保持默认，别动）

| 文件 | 配置项 | 值 | 为什么 |
|---|---|---|---|
| `spawn.json5` | `spawnDimension` | `minecraft:overworld` | ★ 它是**全局**的，指向破碎维度会让**任何世界类型**的玩家都被拉过去（真实发生过的 bug） |
| `permissions.json5` | `forceSkyblockCheck` | `false` | ★ 开了会让 `WorldUtil.isSkyblock` 恒真，同样是全局副作用 |
| `world.json5` | `surfaceSettings` | 基岩1/泥土2/草1 | **这是 `layers` 数组写法的权威范例**（见下） |

### ★ `layers` 必须是数组，不是字符串

老式破碎维度的维度 json 里：

```json
"layers": [
  { "block": "minecraft:bedrock" },
  { "block": "minecraft:dirt", "height": 2 },
  { "block": "minecraft:grass_block" }
]
```

SkyblockBuilder 的字符串语法 `"1*minecraft:bedrock,2*minecraft:dirt,1*minecraft:grass_block"`
只有 `FlatLayers.of(String)` 走；**维度 json 的 codec 走的是 `FlatLayerConfig.CODEC.listOf()`**
（字节码实测），所以只认数组。元素形如 `{"block": "<id>", "height": <int, 默认1>}`，`extras` 可选。

> 写成字符串 → 反序列化失败 → `flatLayers.isEmpty()` → **不铺任何平台，只剩虚空**。

### 高空出现"只有两三格高的浮空薄板"

**不是地形生成 bug，是 `Beardifier` 地形适配。** 见「一点五」的「★ 浮空薄板 bug」。

检查 BrokenOverworldChunkGenerator.createBiomes 里的
SkyStructurePlacer.maskSkyReferences(...) 是否真的生效；取消注释后启动日志应有
「[破碎结构] 结构池：NNN 个（全量；带地形适配的会在 BIOMES 阶段被屏蔽地基）」。
若仍有薄板，说明 Beardifier 在更早的阶段就读了 references（例如别的模组也覆写了 createBiomes）。
